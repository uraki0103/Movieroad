## 1. サービス概要

ムービーロードは、映画鑑賞を思い出として写真ごと記録できる日記アプリである。
評価感想だけではなく、観賞場所、食べた物、観た人、貰ったものまで全て残して振り返ることができる。
積み重ねていった記録が、あなたの道となる。

---

## 2. アイデアの源泉

私の趣味は映画鑑賞だ。
長年映画を観ていると、自分がいつ何の映画を観て、何が面白かったのかうろ覚えになっていく。
試しに、映画の評価とコメントを残せるアプリを使い、記録を残していくことにした。

しかし、長くは続かなかった。
私が飽き性なのもあるが、特別に面白いと感じた映画以外はただなんとなくで評価をつけてしまい、後で振り返る際にあまり意味をなさなかったのである。
毎回しっかり評価をつければよいと思われるだろうが、他人にレビューを公開したいわけではない私にそこまでの意欲はなかった。

そこで、自分のための映画記録をつくる際に何を残したいのか考えた。
その答えは、スマートフォンの写真フォルダとデスクの上にあった。
一緒に行った人との写真、買ったポップコーンの写真、つい買ってしまったパンフレット、記念にとなんとなく机に放置しているチケット、もらった入場者プレゼント。
映画鑑賞とは、観た映画作品だけを指すのではない。
映画館で過ごした時間で起きたこと、受け取ったもの全てが一つの体験を作り上げているのだと感じた。
体験全てをまとめて残せるアプリこそ、最高の映画記録アプリに成り得るのではないだろうか。

---

## 3. 課題の整理

### 3-1. 困りごと

過去に観た映画の感想が時が経つにつれ曖昧となり、思い出せなくなる。
観た際に食べたもの、もらったものの写真やチケットなどを残しがちだが、整理されておらず後日振り返りがしづらい。

---

### 3-2. 本当に解決したい課題

映画の感想だけでなく、映画鑑賞で起きたこと、もらったものを全てまとめて保存できる日記を作成し、何年何十年と積み重ねて後日自分の映画人生を深く振り返ることができるようにしたい。

---

## 4. 想定ユーザーについて

### 4-1. 想定ユーザー

年齢設定：
  - 年齢： 20代~30代
  - 理由： ある程度スマートフォンでの操作に慣れている人を想定。映画館に通うだけの金銭的余裕が必要なため、成人以上とした。

生活・状況設定：
  - 生活・状況： 頻繁に映画館に通う人。友人とよく映画を観て写真を撮る人。
  - 理由： 月1回以下しか劇場に足を運ばない人よりも、頻繁に足を運ぶ人のほうが一度に使う金額も多く、鑑賞体験に複数の要素が伴いやすいと考える。

環境設定：
  - 環境： 都市、地方都市に住み、身近に複数の映画館が存在する。友人などと外出する機会が多く、写真を撮る習慣がある人。
  - 理由： 複数の映画館に行き人ほどどこで誰とみたのか記憶や写真が混同しやすいため。

---

### 4-2. 自分とユーザーの距離

想定ユーザーは自分自身である。2章で触れたように、自分自身の経験が元となっている。同じく映画が好きであり、劇場で様々な写真を撮影している友人数名もイメージに含まれている。

### 4-3. 需要があるのか

- 最初に使ってくれそうな人
SNS等でチケットやフライヤー、入場者プレゼントの写真を挙げている人をよく見かける。
一方で、写真をそのまま撮りっぱなしのままにしている人、既存のアプリで評価のみつけている人。
- 現在の生活で、代わりに使っているもの
  SNSへの画像投稿。
  既存の映画アプリで基本的には星をつける程度。
- それらと置き換えれてまで使う理由
  SNSは投稿が時が経つにつれ流れていってしまい、後日特定の日の記録を探しにくいかつ振り返りにくい。
  既存の映画アプリでは評価、感想は記録できるが、同伴者やチケットなどの付随する情報は残せていない。
  映画鑑賞体験の情報全てをまとめ、後ほど振り返る手段としてはそれぞれ課題があり、その点を解決し埋められることが置き換えて使用する理由となる。



## 4-4. ユーザーがサービスを導入して利用するまでのイメージ(導入・継続の流れ)
- きっかけ
  - 映画鑑賞後、SNSにチケットやフライヤーの写真を投稿しようとした際に、以前の記録を見返せたらと感じた瞬間。
  - 年末などの節目や、観たい映画を探している際に「今年どんな映画を観ただろう」「この映画観てただろう」と考えた際。
  - よく一緒に行く人との思い出を残したいと感じた瞬間。相手から薦められる可能性も。

- 最初の一歩
  - メールアドレスでの登録
  - 最初の記録のハードルを下げるため、「まず1本、最近観た映画を登録してみましょう」という導線を用意する。
  - 任意項目は後から追記できることを案内し、埋めなければという心理的なハードルを下げたい。

- 継続していく理由
  - 記録が積み重なるほどに「自分の映画人生」としての価値が増していく。
  - 月間、年間での振り返り機能など、定期的にまとめる機能を実施することで、記録を続けるモチベーションが上がる。
  - SNSでは埋もれてしまう記録が、このアプリでは目に見えて蓄積されるという点が、SNSとは別の継続理由となる。

## 5. 既存サービス・競合調査

### 5-1. 似たサービスの調査

- サービス名：filmarks
  - URL：https://filmarks.com/
  - アプリ機能

    - ニュース機能
    - 上映時間の検索
    - ドラマ、アニメも対象

- サービス名：repov
  - URL：https://page.repov.me/?tl=ja
  - アプリ機能
    - 評価(星5段階)、レビュー、鑑賞日時、写真、位置情報の記録
    - 友人とシェアするSNSとしての投稿機能
    - フード、本、服など幅広いジャンルが対象

- サービス名：WATCHA PEDIA
  - URL：https://pedia.watcha.com/ja
  - アプリ機能
    - 評価(星5段階)、感想、鑑賞日時の記録
    - 記録を元にした、AIによる作品をおすすめする機能

---

### 5-2. それでも自分が作りたい理由

- 既存サービスの特徴
  - 映画に特化していないアプリでは友人とシェアするSNSとしての側面が強い
  - 記録として残せる項目は評価、感想、日時程度の簡素なものが多い
  - 後ほど振り返るための集計機能は有料またはついていない

映画館に足しげく通う人が、鑑賞にまつわる体験(観た人、飲食物、チケットなど)を、数年後でも詳しく振り返ることができるアプリをつくりたい。

## 6. このサービスで提供したい価値

### 6-1. ユーザーの変化

- 行動の変化：  
  忘れがちな映画を観た感想を、当日の出来事と紐づけて整理された状態で記録できる
- 気持ちの変化：  
  記録が積み重なっていくことで、映画鑑賞へのモチベーションが高まる
- 考え方の変化：  
  映画を「観て終わり」の一過性のものではなく、人生と紐づけられた体験として捉えられるようになる。

### 6-2. 価値を一文で表す

「映画館に足しげく通う人が、映画鑑賞にまつわる体験全てを写真ごと残し、何年経っても振替えることのできるサービス」

## 7. このアプリで実現すること

### MVPで作る機能

- ユーザー登録機能
- 映画鑑賞記録の投稿、編集、削除機能
  - 必須項目として映画タイトル、評価、鑑賞日時を設定
  - 感想、観賞場所、飲食物、チケット、観た人などは任意の項目として設定
  - 観賞場所、観た人はタグとして登録
- TMDb APIを利用した映画タイトルでの検索機能
- 映画鑑賞記録の検索
  - 映画タイトル、鑑賞日時での検索
- 一定期間ごとに鑑賞記録をタイムラインとして一本の道に表示する一覧機能

### 本リリースで作る機能

- 月間、年間で鑑賞記録をまとめたサマリーを作成する機能
  - 鑑賞本数、劇場ランキング、よく観たジャンル、評価TOP5などを検討
- UIの改善
  - タイムラインを曲がりくねった道状に変更するなど、ロードムービーを意識したデザインに
- 映画鑑賞記録の検索機能を強化
  - 観賞場所、観た人でも検索ができるように
- 俳優名、監督名での映画検索機能
- マイルストーン
  - まずは映画鑑賞本数を想定

## 8. このアプリの懸念点とその対策

### 懸念点①:入力項目の多さによる離脱

- 何が問題になりそうか：  
  入力できる項目が多く、手間を感じてしまい次第に使わなくなる可能性がある。
- なぜそう思うか：  
  記録アプリは回数を重ねるにつれ手間を感じ入力が簡素になり、そのまま離脱してしまうことが多い。
- 対策：  
  必須項目(タイトル、評価、日時)を絞り任意項目は後から追加できるようにする。また、劇場名や一緒に観る人はタグ登録できるようにし、入力の手間を減らす。

### 懸念点②:同伴者の写真掲載、名前の入力によるプライバシーの問題

- 何が問題となりそうか:  
  一緒に観た人を写真で記録する機能が、本人の同意がなく顔写真を保存することに繋がりかねない。
- なぜそう思うか:  
  自分にとっては記録のつもりでも、同伴者にとっては望まない写真の保存になる可能性がある。今後記録の共有機能を追加した場合に、この懸念はより大きくなる。
- 対策:  
  前提として、現時点では共有機能は実装しない方針である。同伴者は名前タグを基本とし、写真を添付する場合には本人以外には非公開であることを明記する。

## 9. 今後の展開・発展の方向性

### 観点

- ユーザーはなぜ使い続ける？:  
  記録が積み重なるほど「自分の映画人生」としての資産価値が増していく点。
- 続けることで何が変わる？:  
  自分がどこで、誰とどんな映画を観てきたかという「映画人生の道」が出来上がっていく。
- データが溜まると何ができる？:  
  好みのジャンル、よく行く劇場といった鑑賞の傾向が可視化でき、将来的に作品のレコメンド機能に繋がる可能性がある。

### 現時点での発展案

- 機能追加の方向性：  
  観たい作品を登録するウォッチリスト、マイルストーンの拡充、記録を元にしたレコメンド機能
- UI・体験の改善：  
  タイムラインを曲がりくねった道状にするUI改修、月間年間サマリーの実装

## 10. 技術スタック

### 10-1. 使用予定の技術

- フレームワーク: Ruby + Rails 7.2.x 
- DB: PostgreSQL 18 
- 認証: Devise 
- フロントエンド: Hotwire(Turbo) 
- CSS/UI: Tailwind CSS 
- 画像管理: Active Storage  
- 保存先ストレージ: Cloudinary 
- 開発環境: Docker
- 外部API: TMDb API 
- デプロイ先: Render

---

### 10-2. 技術選定の比較検討、選択理由

- DB  
  候補: MySQL・SQLite・PostgreSQL  
    運用期間が長くなるにつれ鑑賞記録やタグのレコード数が増えていくことを考え、将来的な拡張を見据えデータ型も豊富で複数ユーザーの同時使用に強いPostgreSQLを採用。   
    SQLiteは小規模で複数ユーザーの使用にはやや向かないため不採用。

- フロントエンド
  候補: Hotwire(Turbo)・JavaScript・React  
    今回のアプリでは動的な操作が必要となる場面が少ないと思われるため、Rails7以降ではデフォルトで組み込まれているHotwireを選択。  
    必要に応じてStimulusを使用することで、動的な操作にも対応していく。  

- CSS:
  候補: Tailwind・Bootstrap  
    JavaScriptを最小化する方針のため、JSへの依存度の高いBootstrapは不採用。   
    自由にデザインしやすいTailwindを採用。  

- 画像管理
  候補: Active Storage・CarrierWave・Shrine  
    Railsに標準搭載されており、設定が最小限で済むActive Storageを選択。   
    ファイル保存以外の高度な処理は行われないため、CarrierWaveとShrineは不要と判断。   

- 保存先ストレージ  
  候補: Cloudinary・Amazon S3・Google Cloud Storage  
    現時点では無料で可能な範囲での運用を想定   
    無料期間の期限がなく、月25クレジット分(最大25GB)のストレージが利用可能なCloudinaryを選択。   
    写真を多用するアプリではあるため、本格的な運用時には見直しを検討。   

- 外部API(映画の検索機能)  
  候補: TMDb API・OMDb API・Wikidata  
    非商用利用の範囲では無料であり、日本語のタイトル検索に簡単に対応できるTMDb APIを採用。   
    OMDB APIは日本映画への対応面で劣り、WikiDataは映画に特化しているデータベースではなくポスター画像を利用しづらい。   

- デプロイ先
  候補: Render・Fly.io  
    初心者にも扱いやすく、一旦は無料枠での使用を想定しRender採用。

---

### 10-3.キャッチアップ不足の懸念

1. 外部APIの使用  
  MVPリリース時点で外部APIを使用予定であり、仕様の把握、認証、データ整合性の面でミスがないように連携していく必要がある。
2. フロントエンドの選定  
  今回JavaScriptやReactを選定していないが、道を意識したUIづくりにおいてより有用な可能性がある。本リリース後に改めてキャッチアップを行い、現時点の自分にとって技術的に可能か検討していく。
